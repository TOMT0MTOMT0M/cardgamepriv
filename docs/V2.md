# V2 — le circuit de travail depuis la V1 (07/11/2026)

Les joueurs sont sur la V1 (`docs/V1.md`). Tout nouveau travail se fait sur la branche **`v2`**, se teste sur le **lien
admin** `https://v2.cardgamepriv.pages.dev` (Tom et Hugo seulement), et part chez les joueurs **en une fois**, par patch,
avec `publier-patch.cmd`. La prod ne bouge jamais autrement.

```
 branche v2 ──mettre-en-ligne-v2.cmd──▶ v2.cardgamepriv.pages.dev  +  Convex STAGING (cardgamepriv-v2, .env.v2.local)
     │                                        (bandeau « V2 — test », réservé à l'équipe, données = copie de la prod)
     │ publier-patch.cmd (sauvegarde → fusion → tag vX.Y → mise en ligne)
     ▼
 branche master ─────────────────────▶ cardgamepriv.pages.dev        +  Convex PROD (wry-chicken-825, .env.local)
```

## Les deux mondes

| | Joueurs (prod) | Équipe (V2) |
|---|---|---|
| Site | `https://cardgamepriv.pages.dev` — Pages, branche `master` | `https://v2.cardgamepriv.pages.dev` — Pages, branche `v2` (prévisualisation) |
| Convex | déploiement `dev:wry-chicken-825` (`.env.local`) | projet **`cardgamepriv-v2`**, son déploiement dev (`.env.v2.local`) |
| Build | `vite build` (mode production) | `vite build --mode v2` : lit `.env.v2.local`, `CANAL = 'v2'` (`src/core/canal.ts`) |
| Accès | tout le monde | compte admin / modérateur, sinon écran « Réservé à l'équipe » (`src/game/v2gate.ts`) |
| Discord | webhook + bot + OAuth | OAuth seulement — **pas** de webhook ni de bot (le staging ne notifie jamais les joueurs) |
| Images | R2 `cardgamepriv-art` | le même bucket : V2 n'envoie que les images **nouvelles** ; une image **remplacée** se voit sur V2 après le patch (en local, `npm run dev` la montre tout de suite) |

Garde-fous : `scripts/staging-v2.mjs` refuse de travailler si `.env.v2.local` pointe sur le déploiement de `.env.local` ;
`mettre-en-ligne-prod.cmd` demande confirmation hors de `master` ; le lien V2 porte un badge « V2 — test » en bas à gauche.

## Lanceurs (double-clic, journal dans `logs\`)

| Lanceur | Quand | Ce qu'il fait |
|---|---|---|
| `creer-staging-v2.cmd` | **une fois** | crée le projet Convex `cardgamepriv-v2`, écrit `.env.v2.local`, copie les variables d'environnement (sauf webhook/bot), importe un export de la base des joueurs, Tom et Hugo modérateurs. Peut ouvrir le navigateur (connexion Convex). |
| `mettre-en-ligne-v2.cmd` | après chaque lot de travail sur `v2` | code Convex → staging + migrations, `tsc`, build mode v2, images nouvelles → R2, Pages branche `v2`. **Ne touche jamais la prod.** |
| `rafraichir-staging-v2.cmd` | données de test trop vieilles / abîmées | remplace toutes les données du staging par un export frais de la prod |
| `publier-patch.cmd` | quand Tom décide de sortir un patch | contrôles → simulation (commits, fichiers, schéma/migrations) → export de la base → **PUBLIER** → fusion `v2`→`master`, mise en ligne prod, tag `vX.Y`, `v2` réalignée, push |
| `sauvegarder-v1.cmd` | de temps en temps | export de la base + archive du code au tag `v1.0` (`docs/V1.md`) |
| `push.cmd` | après des commits faits depuis la session Claude | pousse toutes les branches et les tags |
| `mettre-en-ligne-prod.cmd` | plus à la main | moteur de la mise en ligne prod, appelé par `publier-patch.cmd` |

## Règles

1. **Tout nouveau travail sur `v2`.** `master` ne reçoit que des fusions de `v2` par `publier-patch.cmd`. Correctif urgent
   en prod : le faire sur `v2` et publier un patch `vX.Y+1` (c'est aussi rapide, et la base est sauvegardée avant).
2. **Schéma Convex compatible.** Le code V1 (dans l'onglet d'un joueur qui n'a pas rechargé) et le code du patch tournent
   sur la même base pendant quelques minutes, et une V1 doit pouvoir être remise si le patch tourne mal :
   - nouveaux champs **optionnels** (`v.optional(...)`), jamais de champ obligatoire ajouté ni de type changé ;
   - un champ qui change de sens = un **nouveau** champ, l'ancien lu en repli puis retiré deux patchs plus tard ;
   - transformation de données = **migration idempotente** dans `convex/migrations.ts`, ajoutée à `mettre-en-ligne-prod.cmd`
     ET `mettre-en-ligne-v2.cmd`, testée sur le staging (`rafraichir-staging-v2.cmd` pour repartir de données réelles) ;
   - `publier-patch.cmd` liste `convex/schema.ts` / `convex/migrations.ts` dans sa simulation s'ils ont changé.
3. **Un patch = un lot complet**, numéroté `vX.Y` (tag git), avec son entrée dans `src/game/updates.data.ts` (onglet « Mises
   à jour » du jeu).
4. **Pendant la mise en ligne**, le jeu ouvert chez un joueur continue de marcher : `src/game/maj.ts` relit `/version.json`
   toutes les 3 min (et au retour sur l'onglet) et affiche « Mise à jour disponible · Recharger » ; si un morceau du jeu
   chargé à la demande a disparu du site (`vite:preloadError`), il recharge tout seul, une fois.

## Retour arrière

Voir `docs/V1.md` (site seul, site + fonctions, ou données). Pour un patch : `git reset --hard vX.Y-1` sur `master` puis
`mettre-en-ligne-prod.cmd` ; données : `sauvegardes\avant-patch-vX.Y-….zip`.
